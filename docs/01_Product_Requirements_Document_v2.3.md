## 1. 产品定义

OmniLore 是一个以原始证据为基础、以可审阅的 Markdown 知识页为主要人类编辑界面、
以 PostgreSQL 提供授权、任务状态、版本关系和可重建检索索引的 **AI 原生可审计知识中枢**。

它的核心价值不是“把文件塞进向量库”，而是把分散资料转化为**有来源、有状态、有版本、
有权限、有纠错路径**的可持续知识资产。

### 1.1 核心价值主张

1. **降低整理成本**：文件投递或对话提交 → 自动解析、候选分类、知识编译、来源关联。
2. **提高知识可信度**：Wiki 页面必须保留原始证据引用；不确定的路由/识别/版本关系进入人工复核。
3. **减少检索错误**：关键词 + 全文 + 向量混合检索，且检索阶段按**授权**与**当前有效版本**过滤。
4. **持续演进而非一次性问答**：支持补充、替代、纠错、审计、恢复，避免新旧版本混杂。
5. **保护不同场景边界**：个人 / 家庭 / 企业共享技术底座，但授权范围、成员关系与内容规则独立管理。

### 1.2 项目准入条件（硬性）

在开放家庭健康数据或企业机密资料的真实使用之前，必须先通过 Phase 0 安全与技术验证：

- 数据库授权与 RLS 覆盖范围经**逐表盘点**并通过**负向测试**；
- 文件访问网关**不接受客户端裸路径**，路径/空间/类别/文档归属均须服务端校验；
- 文件系统与数据库采用**可恢复的分阶段提交**，不宣称跨系统原子事务；
- Markdown 与 PostgreSQL 的**权威字段边界**明确，双向同步具备冲突检测与恢复策略；
- 任务状态机、幂等规则、版本状态与回滚规则定义一致；
- MVP 的用户旅程、错误反馈、恢复与验收标准明确。

## 2. 权限与空间模型

### 2.1 有效权限公式（D-08）

```
有效权限 = Token 范围
         ∩ 当前有效 Membership
         ∩ 空间继承规则
         ∩ Profile / Category 规则
```

**Token 本身不等同于内容授权。** LLM 只提供建议，不得决定文件路径、类别、空间或版本授权。

### 2.2 Profile 规则

| Profile | 可读 Category | 隔离规则 |
|---|---|---|
| `WORK` | `01_Work` | 硬性隔离 `02_Life` / `03_Family` / `04_Health_Archive`（同空间下亦然） |
| `FAMILY` | `03_Family`、`04_Health_Archive` | 硬性隔离个人私库与企业空间 |
| `OMNI` | 空间自身允许的全部 Category | 仍需落在 Token ∩ Membership ∩ 空间规则的交集内 |

### 2.3 Space 分阶段模型（D-10）

交付顺序：**个人知识闭环 → 家庭健康 → 企业组织树**。
数据模型可扩展 ≠ 一期必须实现全部场景。

## 3. 功能需求矩阵 FR-01 ~ FR-19

> 优先级：P0 = 首启必需；P1 = 应交付；P2 = 计划交付。

| 编号 | 名称 | 优先级 | 阶段 | 需求描述 | 当前实现状态（`v0.3.0-alpha`） |
|---|---|---|---|---|---|
| **FR-01** | 文件与图片入库 | P0 | Phase 1 | 生成任务 ID；记录文件哈希、来源和状态；重复提交可幂等返回 | `Implemented`：Markdown / 代码与图像有自动化用例；PDF 已实现 `pdfplumber` → `pypdf`，但当前没有真实 PDF 自动化样本 |
| **FR-02** | 随手投递与显式目标 | P0 | Phase 1 | 显式指定目标时先授权校验；AUTO 目标不明确时进入待确认 | ✅ 越权显式目标直接拒绝；混合/归属不明内容隔离为 `NEEDS_REVIEW` |
| **FR-03** | 安全预检 | P0 | Phase 0/1 | 令牌、目标空间、文件可读性和类别规则在编译前检查 | ✅ `ResolvedScope` + 命令级 RLS + 文件网关 |
| **FR-04** | 知识编译 | P0 | Phase 1 | 生成可读 Markdown，保留源文件、章节或页码级来源信息 | ✅ `source_asset_ids` / `source_locator{page,heading}` |
| **FR-05** | 混合检索 | P0 | Phase 1 | 授权过滤后结合全文/关键词/向量候选，返回文档版本与引用位置 | `Simulated`：无 Key 的 BM25 / 关键词路径真实执行；有 Key 的 `hybrid` 路径只有假 HTTP transport，没有真实供应商调用 |
| **FR-06** | 纠错与重分类 | P0 | Phase 1 | 允许修正正文、类别、标题和候选目标；权限变更需显式批准 | ✅ 全部 7 个审核动作（`APPROVE_REVIEW`/`RECLASSIFY`/`SPLIT_DOCUMENT`/`FIX_EXTRACTED_FIELD`/`REVERT_VERSION`/`PROMOTE_COPY`/`CANCEL_TASK`） |
| **FR-07** | 幂等任务和失败恢复 | P0 | Phase 1 | 支持重试、失败定位、重复请求和进程中断恢复 | ✅ 幂等键 + Outbox 恢复 Worker + `SKIP LOCKED` 租约 |
| **FR-08** | 逻辑文档版本管理 | P0 | Phase 1 | 支持新建、替代、补充和回滚；当前版本唯一 | ✅ 两阶段零停机版本切换；系列 + 唯一当前版本指针 |
| **FR-09** | Markdown 人工编辑回写 | P0 | Phase 1 | 用户编辑正文后更新切片；系统字段不因手工编辑直接改变 | ✅ 写回哈希比对防死循环 + 受保护 Frontmatter 字段 + `.conflict_r*.md` 冲突副本 |
| **FR-10** | 来源与审计 | P0 | Phase 1 | 可追溯原始文件、任务、版本、操作者和变更摘要 | ✅ `audit_events` 全量 before/after 摘要 |
| **FR-11** | Obsidian 治理控制台 | P1 | Phase 1 | 展示待确认、失败任务、近期版本变更和备份状态 | ✅ `_dashboard_控制台.md` 自动生成 |
| **FR-12** | TTL 与知识 Lint | P1 | Phase 2 | 过期提醒、孤儿链接、潜在冲突仅生成建议，默认不静默改写 | ✅ `run_knowledge_lint` 只出建议 |
| **FR-13** | 家庭空间成员管理 | P1 | Phase 2 | 邀请、角色分配、撤权、共享记录审计 | ✅ 仅 FAMILY 空间 ADMIN 可操作 |
| **FR-14** | 健康指标提取和复核 | P1 | Phase 2 | 结构化指标保留来源、单位、参考范围和核验状态 | ✅ 默认 `NEEDS_CHECK` + “AI 提取，尚未核验”标注 → 人工 `FIX_EXTRACTED_FIELD` 转 `HUMAN_VERIFIED` |
| **FR-15** | Space 晋升 / 发布 | P1 | Phase 2/3 | 预览复制内容和敏感信息；用户确认后创建目标空间副本及审计记录 | ✅ `PROMOTE_COPY` 含身份证/手机/银行卡/`sk-`/`tok-`/`ak-` 脱敏预览 |
| **FR-16** | 企业组织树及继承读取 | P2 | Phase 3 | 支持组织级授权继承；继承写入必须单独授权 | ✅ `ltree` + `parent_space_id` 链；仅 `ORG_PUBLIC` 只读继承，`ORG_RESTRICTED` 不参与 |
| **FR-17** | 代码符号关联检索 | P1 | Phase 1 | 按接口、类名、路径或 ADR 关联相关技术知识 | ✅ Python `ast` + 多语言正则提取类名/方法名/REST 路由/`ADR-xxx` |

## 4. 已锁定的规则决议（D-01 ~ D-13）

| 编号 | 决策 | 规则 |
|---|---|---|
| **D-01** | 原始文件 | 原始字节不可变；内容哈希用于去重与完整性验证 |
| **D-02** | 知识正文 | Wiki Markdown 是可读可编辑的知识正文载体 |
| **D-03** | 系统元数据 | `doc_id`、空间归属、授权关系、版本指针、任务状态由数据库与受控业务操作管理；Frontmatter 中对应字段是**受控投影**，不能因手动改文本直接改变权限或版本 |
| **D-04** | 检索索引 | 向量 / 全文 / 章节切片均为**派生数据**，可重建，不能作为权限事实源 |
| **D-05** | 不确定路由 | 禁止自动跨边界共享；进入隔离待确认流程 |
| **D-06** | 版本唯一性 | 每个逻辑文档系列由数据库事务与唯一约束保证只有一个当前版本；补充文档作为独立关联实体 |
| **D-07** | 跨系统一致性 | 文件系统与 PostgreSQL 不存在单一原子事务；采用持久化状态、重试、补偿与恢复任务 |
| **D-08** | 授权模型 | 见第 2.1 节的四维交集公式；Token ≠ 内容授权 |
| **D-09** | RLS 定位 | RLS 是纵深防御，不替代身份认证、授权服务、参数化查询、文件代理与安全测试 |
| **D-10** | 交付顺序 | 先个人 → 再家庭 → 再企业（见第 2.3 节） |
| **D-11** | 模型接入 | 所有模型调用经统一 Model Adapter；客户端、n8n 节点与业务工具不得各自持有或直接使用供应商 API Key |
| **D-12** | 模型职责 | LLM 负责理解、摘要、分类建议与答案组织；授权、版本提交、文件写入与任务状态由**确定性服务端逻辑**执行 |
| **D-13** | 首期模型范围 | 一个主 Chat/Vision 模型 + 一个 Embedding 模型；复杂任务可选升档；Reranker 暂不作为 MVP 必需项 |

### 4.1 最终产品决议

1. 保留统一底座，限制一期承诺。
2. 优先保证知识可信 —— 证据、追溯、版本、纠错、恢复先于更高比例的自动路由。
3. 权限必须由服务端强制执行 —— LLM 仅提供建议。
4. “自动回滚”改为“可恢复和可补偿” —— 不宣称文件系统与 PostgreSQL 的统一原子事务。
5. 安全承诺必须转化为测试证据 —— 对外宣称前须有负向测试与恢复演练记录。
6. 阶段计划以验收条件为准 —— 周期是估算，安全验证与真实恢复演练不可被工期压缩。
7. **W0 追加六项决策**（详见 [`docs/DECISIONS.md`](DECISIONS.md)）：
   Apache-2.0 许可、版本对外口径 `v0.3.0-alpha`、opt-in 匿名遥测（本次不实现，Q2）、
   8 周首发窗口 @ 0.5 FTE、项目命名为 OmniLore，以及多存储后端方向冻结到首发后。

## 5. 标准用户旅程

### 旅程 A：普通文件入库（FR-01 ~ FR-04）

1. 用户投递文件（显式目标或 AUTO）
2. 安全预检 → 生成任务 ID → 解析 → 知识编译
3. Saga 两阶段提交 → `COMMITTED`
4. 返回任务回执（含下一步可执行动作）

### 旅程 B：归属不明或跨场景内容（FR-02, D-05）

1. 路由不唯一 → `NEEDS_REVIEW`（隔离待确认，**不自动跨边界共享**）
2. 用户执行 `APPROVE_REVIEW` / `RECLASSIFY` / `SPLIT_DOCUMENT` / `CANCEL_TASK`
3. 权限变更需显式批准

### 旅程 C：Obsidian 修改正文（FR-09, D-02, D-03）

1. 用户在 Obsidian 编辑 `wiki/*.md`
2. Watcher 检测到 hash 变化 → `sync_obsidian_markdown_edit`
3. 受控 Frontmatter 字段不被接受为变更来源；内容 hash 相同则视为自写回 no-op
4. 并发冲突生成 `.conflict_r*.md` 副本

## 7. W0 阶段的已知实现边界

诚实披露：以下边界在本次 alpha 发布中**尚未**消除。

1. **当前 CLI / MCP 应用运行时只有内存引擎。** `RLSDatabaseEngine` 与 PostgreSQL RLS 策略同构，
   但进程退出后状态清空。仓库虽有 `AsyncpgRepository`、SQL、PostgreSQL 容器与 `DATABASE_URL`
   转发，入口尚未实例化该仓储层；因此容器模式当前也不提供业务状态持久化。
2. **部分断言依赖宿主能力。** 符号链接防御的断言依赖宿主能否创建 symlink；
   无权限的宿主上会**显式 skip**（`tests/_platform_support.py`），非平台缺陷。
3. **向量质量依赖外部供应商。** 未配置 `DASHSCOPE_API_KEY` 时降级为关键词检索，
   语义召回能力会下降；降级与否由 `retrieval_mode` / `degraded_reason` 字段如实上报。
4. **遥测尚未实现。** 决策已接受 opt-in 匿名遥测，实现排期在 Q2（见 `docs/DECISIONS.md`）。
